# CI review — 16 October 2026

This review covers what Bonsai verifies, when that verification runs, which work repeats, and how to shorten feedback without weakening release or security checks. It is a review and implementation plan; no workflows or repository settings were changed.

## Main conclusions

1. **Fix the merge gate before removing checks.** Protected `main` requires only `CI passes`. That job aggregates backend builds, the release snapshot, and archive smoke tests, but excludes the frontend workflow. PR #101 actually merged before its frontend check finished.
2. **The complete frontend workflow repeats after merges.** It runs for matching PRs and again on pushes to `main`. Backend `CI` is already PR-only. The backend builds seen after merging belong to release production, which has a different purpose.
3. **Frontend time is dominated by browser work and repeated measurements.** One representative PR spent 189 seconds on E2E and another 165 seconds on three extra startup-measurement invocations. Dependency installation took 3 seconds.
4. **Separate routine correctness checks from extensive performance evidence.** Each frontend run currently executes 264 measured/warmup startup samples across four configurations and builds the UI five times. CI does not enforce the documented 300 ms performance threshold.
5. **Stop unnecessary run creation.** Every label change restarts the entire backend matrix and release snapshot. Superseded frontend runs are never canceled.
6. **Keep native backend coverage and actual release-archive verification.** They catch different failures. The Windows test suite is a better backend optimization target than removing a platform or its tests.

The first implementation should combine a complete required gate, PR-scoped frontend cancellation, separate label validation, conservative change classification, and lighter PR measurements. Full performance sampling can then run on demand and on a schedule against `main`.

## Findings and recommendations

Priority means implementation order: **P1** addresses the merge guarantee or the largest avoidable work; **P2** improves efficiency, diagnosis, or coverage after that foundation.

### F01 — P1: frontend verification is outside the required merge gate

**Evidence.** `main` protection has `strict: true`, enforces administrators, and requires only `CI passes`. The CI aggregate depends on `build`, `release-dry-run`, and `archive-smoke`; it has no frontend dependency. There were no additional active branch rules returned by the branch-rules API.

This is observable in [PR #101](https://github.com/Tiago-0liveira/bonsai/pull/101):

| Event | Time on 15 October |
| --- | --- |
| Backend CI completed successfully | 22:54:05 |
| PR merged | **22:56:24** |
| Main frontend rerun and release workflow created | 22:56:26 |
| PR frontend completed successfully | **22:58:15** |
| Release workflow completed | 22:59:55 |
| Main frontend rerun completed | **23:02:11** |

The frontend was still running at merge time. The release also completed before the `main` frontend rerun finished. PR #100 likewise merged before its PR frontend check completed. The assumption that merging implies every frontend check passed is currently false.

**Recommendation.** Establish a stable required gate that includes all applicable frontend correctness jobs. Prefer one always-created PR orchestrator, with frontend checks as ordinary or reusable-workflow jobs, and a final `CI passes` job that validates their results. Keep the existing required name during migration.

Do not simply make today's path-filtered `verify` check required: a workflow excluded by path filters may leave a required check pending. Put change classification inside the always-created workflow and explicitly allow a skipped job only when classification says it was unnecessary. Detector failure, unexpected skip, cancellation, and an applicable failed check must fail the gate. GitHub documents this [path-filter behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore).

Retain strict up-to-date protection. If a merge queue is adopted later, add `merge_group: checks_requested` handling to every required workflow before enabling it. GitHub treats [merge-group validation as a separate event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group).

### F02 — P1: full frontend verification repeats on `main`

**Evidence.** `frontend.yml:7–24` subscribes both to matching PR changes and matching pushes to `main`. There is no deduplication. In the 200-run sample, eight `main` frontend reruns consumed **3,275 job seconds — 54m 35s of aggregate runner occupancy**. This is observed work, not a guaranteed removable billing amount or a monthly projection.

For [PR #92](https://github.com/Tiago-0liveira/bonsai/pull/92), [PR frontend verification](https://github.com/Tiago-0liveira/bonsai/actions/runs/38787731397) succeeded, then the [main push](https://github.com/Tiago-0liveira/bonsai/actions/runs/38788884214) ran the whole frontend pipeline again. The push job took 500 seconds.

**Recommendation.** After F01 and F06, make full frontend correctness verification a pre-merge responsibility. Remove the full `push: main` verification, or replace it with a deliberately small smoke/cache-warming job. Keep full performance evidence on demand and on a schedule.

This is a policy decision, not automatic equivalence between commits. PR workflows test a synthetic merge revision; merging, squashing, rebasing, or base movement can produce a different SHA. This repository allows all three merge methods. Retain strict protection, verify changes against the current base, and document the residual benefit of exact-main smoke checks. A merge queue is an alternative integration guarantee, not a prerequisite to every optimization.

If bypass/direct-push paths are allowed in future, define their validation separately. Current backend CI already does not run on direct pushes. Do not add a privileged release path that assumes an unvalidated direct push was checked.

### F03 — P1: extensive performance sampling runs on every frontend change

**Evidence.** `BONSAI_P7_RUNS=30` applies to the main E2E invocation and three extra invocations. `warm-start.spec.ts` defaults to three warmups and runs both cold and warm scenarios. Across profiling-small, profiling-large, production-small, and production-large, that is:

```text
4 configurations × 2 scenarios × (3 warmups + 30 samples) = 264 page-load samples
```

Every sample opens a fresh browser context and restarts the fixture API. The warm-start file is serial. The 300 ms p95 assertion only runs with `BONSAI_P7_GATE=1`, which the workflow does not set. CI still checks correctness, missing paints, and the first-screen request graph, but collecting 30 samples is not currently enforcing the latency target.

**Recommendation.** Keep small, explicit cold/warm startup correctness checks in PR CI, including the production build's request graph and absence of missing paints. Use a few samples, not a statistical p95 claim. Preserve the remaining warm-start correctness tests: stale labels, independent revalidation, damaged caches, removed projects, old-epoch events, and blocked browser storage.

Move the 30-sample small/large profiling/production matrix into a dedicated performance workflow, initially manual plus scheduled against `main`. Make PR performance runs explicitly requestable without restarting unrelated backend checks. A named job can remain required on sensitive changes if a particular production scenario supplies unique correctness coverage.

**Measured opportunity.** The three extra measurement steps consumed **105–176 seconds** across five inspected successful jobs. Removing just those steps would arithmetically change their job durations from 340–500 seconds to **235–328 seconds**, before replacing any unique correctness coverage. This is a calculation from recorded steps, not a measured optimized pipeline. Reducing the main invocation's sample count offers further savings that need an actual trial.

### F04 — P1: old frontend runs continue after new commits arrive

**Evidence.** Backend CI has PR-scoped concurrency with cancellation. Frontend has none. For the provider-data PR, the run created at **19:29:41 on 15 October** continued until 19:37:48 even though a newer revision started at 19:33:49. Both consumed the complete frontend workflow. None of the 68 frontend PR runs in the larger sample was canceled.

**Recommendation.** Add workflow-level cancellation scoped to workflow plus PR number, falling back to branch ref for push/manual jobs. Do not use one global frontend group: independent PRs must remain independent. Keep release's separate serialized, non-canceling group; release version selection/publication must not be interrupted by normal PR activity.

If measurements become separate jobs/workflows, give them an explicit concurrency policy too. A superseded PR measurement can be canceled; a release publication must finish or fail visibly.

### F05 — P1: every label change restarts the complete backend matrix

**Evidence.** `ci.yml:3–4` includes `labeled` and `unlabeled`. Label validation lives inside `release-dry-run`, so even changing an unrelated label launches three native test jobs, a snapshot build, and three smoke jobs. The common concurrency group can cancel a useful in-progress run when a label-only event arrives.

The sample contains six pairs of CI runs with identical head SHAs created within zero or one second; one run in each pair was canceled. For example, [38835967953](https://github.com/Tiago-0liveira/bonsai/actions/runs/38835967953) was followed by [38835969423](https://github.com/Tiago-0liveira/bonsai/actions/runs/38835969423). The API does not expose the activity subtype in these run records, so attributing each observed pair specifically to labeling is an inference. The configured trigger itself guarantees that label edits can cause this work.

**Recommendation.** Give release-label validation its own inexpensive required check and workflow. Run it for initial PR events and changes to relevant `release:*` labels. Remove label events from the heavy code-validation workflow. Preserve the rejection of multiple release labels and the current release-version tests.

Update branch protection to require both the complete code gate and the metadata check. The metadata check needs its own concurrency group so it cannot cancel a build. Keep code validation independent of whether a particular merge will publish: `release:none` should not suppress packaging tests for a code change.

### F06 — P1: frontend path selection both over-triggers and misses dependencies

**Evidence.** The current filter is `web/**`, two server subtrees, and `frontend.yml`. This causes frontend documentation changes to run all browser/performance checks. PR #100 changed documentation and agent instructions, including `web/AGENTS.md` and `web/CLAUDE.md`; its [PR frontend run](https://github.com/Tiago-0liveira/bonsai/actions/runs/38799373429) and [main rerun](https://github.com/Tiago-0liveira/bonsai/actions/runs/38800093524) both ran.

Conversely, `go.mod`, `go.sum`, providers, agent runtime, daemon, Git services, and core packages can alter the real Go-backed browser fixtures without matching those filters. `CI` does compile/test the backend and build a snapshot, but it does not supply equivalent browser interactions. The native build/snapshot matrix also runs for every docs-only or pure frontend PR, because CI has no change classification at all.

**Recommendation.** Use one conservative classifier inside the required orchestrator. Treat documentation-only edits as a positive, small allowlist; do not globally ignore Markdown, because Markdown under product/test-fixture paths may be input data. Unknown paths, classifier errors, dependency/configuration changes, and workflow changes should fail closed to the relevant full checks.

Start conservatively: all Go source/module changes can request browser correctness checks. Refine that later using an audited dependency list or `go list`-based dependency analysis that includes test imports, fixtures, build tags, and shared runtime packages. Exclude TUI-only packages only after proving they are outside the tested dependency graph.

For pure TS/CSS changes, keep frontend checks and snapshot/embed/archive coverage but consider skipping the ordinary three-OS untagged Go test matrix. Changes to `web/*.go`, Go modules, installers, release configuration, or shared infrastructure must select their native checks. A change to release packaging must still test packaging even if this merge carries `release:none`.

Keep PR coverage for feature-branch targets: current CI intentionally supports them. The old integration branch's push trigger can be retired separately after confirming it is no longer used.

### F07 — P2: measurement commands rebuild outputs already produced in the job

**Evidence.** The ordinary frontend job builds production once. Main E2E builds `dist-e2e`; the large profiling measurement builds it again; each production measurement rebuilds `dist`. That is **five UI builds per frontend job**, plus repeated Go fixture launches. The snapshot and actual release have their own additional production builds.

**Recommendation.** Build each required UI mode once per job, and make Playwright's server command start fixtures without an unconditional rebuild when a verified output is supplied. Keep a convenient build-and-start command for local development. Restart fixture state between measurement configurations even when immutable UI files are reused.

In a future split pipeline, use exact-run artifacts with source revision, mode, lockfile, toolchain, and build identity, or build independently if artifact transfer costs more than the build. Never mix `dist` with `dist-e2e`: production/embed tests must still reject test hooks. Do not reuse a stale local output merely because its directory exists.

Build reuse alone is secondary: the initial production build was only 4–8 seconds in the inspected jobs. Reducing measurement policy has much greater value.

### F08 — P2: expensive measurement steps continue after functional E2E failure

**Evidence.** Extra measurements and cache measurements use `!cancelled() && steps.browser.outcome == 'success'`. A custom status condition allows them to run after an earlier test failure. In [frontend run 38784035296](https://github.com/Tiago-0liveira/bonsai/actions/runs/38784035296), E2E failed, then the three extra measurement steps consumed another **166 seconds**. All seven failed frontend runs in the current-period sample failed at the main E2E step, rather than an extra measurement step.

**Recommendation.** Keep evidence upload unconditional, but run optional expensive follow-up measurements only after the required correctness checks succeed. A separate performance workflow makes this boundary clearer. Preserve any intentionally useful failure diagnostics; those are different from collecting another full performance dataset on a known failing revision.

### F09 — P2: the frontend pipeline is a single serial job

**Evidence.** Typecheck, lint, unit tests, build, browser setup, all E2E, and measurements run in one job. A slow browser phase delays the entire frontend status. The general Playwright configuration starts four Go fixture servers even when an invocation only needs one category.

**Recommendation.** After removing repeated work, trial two coarse frontend jobs: static/unit/build verification and functional browser verification. Give each a useful, stable name and aggregate both into the required gate. Measure setup, artifact, and compilation overhead before adding more jobs.

If E2E is still the critical path, separate mocked UI specs, full-stack/PTY specs, and startup/performance specs using projects/configurations that start only their required servers. Consider two shards on separate runners rather than blindly increasing workers on one runner. The fixtures share ports 7011–7014 and mutable process/project state; moving a serial test onto multiple workers without isolation can introduce incorrect interference. The benchmark should retain one worker and avoid competing with unrelated tests. Playwright's [CI guidance](https://playwright.dev/docs/ci#workers) favors reproducibility and suggests sharding for wider parallelism.

Do not assume `fullyParallel` or more workers is automatically faster. The observed main suite already used two workers.

### F10 — P2: unit-test optimization should follow the browser improvements

**Evidence.** Vitest took roughly 28–50 seconds across inspected frontend jobs. The 49-second example reported 80 files and 793 tests. Every file uses `jsdom`, including pure logic tests; worker-summed environment initialization was 52.56 seconds, which is **not** an extra 52.56 seconds of wall time. The slowest files included `AgentsPage`, `StartProcessDialog`, `StartAgentDialog`, and `ProfileManagement`.

**Recommendation.** Profile these files and move demonstrably DOM-independent tests to a Node environment through supported Vitest project/per-file configuration. Review repeated render/setup work and tune workers against the actual runner. Retain test isolation unless measurements and tests demonstrate it is safe to change.

Do not replace the full PR suite with changed-file-only tests: stores, reconciliation, preferences, API clients, and component behavior have cross-feature effects. A small runner experiment is justified; removing assertions to hit a duration target is not.

### F11 — P2: backend latency is mostly native tests, especially Windows

**Evidence.** In [CI run 38812811518](https://github.com/Tiago-0liveira/bonsai/actions/runs/38812811518), job durations were Linux 155s, macOS 71s, Windows 237s, and snapshot 161s. Windows spent 51s in vet and 134s in tests; the explicit `go build ./...` took 3s. In another recent run, Windows spent 48s in vet and 142s in tests.

Windows package timings from the first run included `internal/cli` 108.4s, `internal/daemon/server` 78.8s, `internal/git/local` 63.7s, and `internal/core/pkgmgr` 53.4s. Packages overlap, so these numbers cannot be summed into job duration. CLI and daemon test helpers each build real binaries; several integration tests launch processes and wait for lifecycle transitions. The package-manager argv test executes whichever package managers happen to be installed on the runner, making coverage and runtime image-dependent.

**Recommendation.** Keep all three native platforms and Linux race coverage. Collect `go test -json` timing evidence, then target the Windows integration packages: measure subprocess/build costs, replace fixed waits with state-driven synchronization where appropriate, and make native package-manager integration coverage explicit instead of accidentally depending on the runner image.

Investigate process cleanup failures before calling them flakes. For example, [run 38834067916](https://github.com/Tiago-0liveira/bonsai/actions/runs/38834067916) failed Windows `TestKillByIDLeavesSiblings`: the killed process remained running and held a temporary-directory file open. The log establishes a failure, not whether the test or product is responsible.

Do not remove the explicit build step for a major speedup: it was only 1–3 seconds in inspected runs and documents an important Node-independent build contract. `go test`'s default vet checks are a subset of explicit vet; avoid treating those commands as completely identical. See the [Go test command reference](https://pkg.go.dev/cmd/go#hdr-Test_packages).

### F12 — P2: caches exist, but Go build-cache freshness deserves measurement

**Evidence.** Node/pnpm store caching and Go module/build caching are already enabled. Logs show exact cache hits, and frontend installation took 2–3 seconds. `setup-go@v5` uses Go/module-based cache identity; inspected Linux frontend, build, and snapshot jobs restored the same primary key. Their post steps reported an exact hit and did not save updated build outputs.

**Recommendation.** Do not add another generic dependency cache as the first fix. If backend optimization continues, measure whether a dependency-only, immutable key repeatedly restores outdated source build outputs. Trial an explicit build-cache policy with bounded source/day-based generations and restore prefixes; separate native/race/cross-build workloads only if hit rates and cache size justify it. Disable the overlapping automatic cache when replacing it, and retain module caching.

PR caches have merge-ref scope and do not automatically warm `main` or sibling PRs. If full main verification is removed, choose a trusted default-branch cache owner, such as a small push/scheduled job, and measure its net benefit. Do not assume the `pull_request_target` release job can populate the default-branch cache under current cache-access rules. These restrictions are described in GitHub's [cache access reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache).

Browser installation took 16–23 seconds in inspected jobs. Playwright explicitly [does not generally recommend caching browser binaries](https://playwright.dev/docs/ci#caching-browsers), because restore cost and uncached OS dependencies can erase the gain. Benchmark a version-matched preinstalled image only after accounting for Bonsai's Go/native fixture needs.

### F13 — P2: failure evidence and execution limits are incomplete

**Evidence.** The main Playwright config specifies `trace: 'on-first-retry'` but configures no retries. Ordinary failed tests therefore do not get that trace unless retry behavior is supplied elsewhere. The measurement tests have explicit manual traces; those are separate. The workflow uploads `playwright-report/`, but no HTML reporter is configured. None of the current workflow jobs has an explicit `timeout-minutes`.

**Recommendation.** Use failure-retained traces for ordinary E2E, or explicitly configure a small retry count with visible flaky-test reporting. Prefer a retained failure trace if the goal is diagnosis without automatically masking instability. Configure the intended HTML/JSON/blob reporter instead of relying on an uploaded directory being present.

Set sensible job and test-command timeouts based on measured upper bounds, with extra allowance for cold caches. Keep signal-based fixture shutdown and unconditional diagnostics. A typical frontend check should not rely on the platform's six-hour default job limit; GitHub documents that [default timeout](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idtimeout-minutes). Trim successful trace retention only after preserving the evidence needed for performance analysis.

### F14 — P2: some intended quality checks are not exercised by CI

**Evidence.** `package.json` defines `test:coverage`, and Vitest declares 100% thresholds for `src/lib/github/**`. CI runs `pnpm test`, so those thresholds are not enforced there. The TypeScript app project includes `src`; the tooling project includes `vite.config.ts` and `playwright.config.ts`, but not `playwright.measure.config.ts` or the E2E sources. ESLint also targets `src` only. Playwright executing TS is not equivalent to checking those files with `tsc`.

**Recommendation.** Decide whether the pure GitHub-logic coverage threshold is intended as a merge guarantee. If it is, enforce it in a targeted coverage job or replace the ordinary unit invocation with the appropriate coverage invocation; do not accidentally execute the entire suite twice. Include E2E/measurement configuration in a dedicated typecheck project, then resolve existing errors before making it required. These are coverage-quality improvements, not promised speedups.

### F15 — P2: `release:none` pays setup cost before deciding to skip

**Evidence.** Release version selection runs after Go, pnpm, and Node setup. [PR #100's release workflow](https://github.com/Tiago-0liveira/bonsai/actions/runs/38800092063) succeeded with `release:none`, but its release job still occupied 36 seconds before archive/publish jobs were skipped.

**Recommendation.** Move the trusted label/version/idempotency decision ahead of expensive toolchain setup, then condition setup/build steps on the decision. Preserve exact-merge checkout, conflicting-label rejection, existing-tag rerun behavior, and draft handling. `actions/github-script` supplies its own runtime; the version-selection script itself does not need a full frontend toolchain installation first.

Keep the existing global release serialization, including `queue: max`. Concurrent version selection is not a worthwhile speed tradeoff.

## Repetition that should remain

The PR snapshot and the post-merge release look similar, but validate different products:

| Check | What it proves | Recommendation |
| --- | --- | --- |
| Native `go test ./...` matrix | OS-specific source/runtime behavior in normal untagged builds | Keep for applicable Go changes |
| Linux race detector | Concurrent execution under instrumentation | Keep; split into a parallel job only if its extra setup improves the measured critical path |
| PR GoReleaser snapshot | Six targets compile/package with `embedui`; packaging hooks succeed before merge | Keep for applicable source, frontend, and packaging changes |
| PR native archive smoke | Produced snapshot binaries serve production assets, enforce capability/origin rules, and shut down correctly | Keep after the snapshot |
| Release build | Exact merged source with final tag/version/commit/date and actual distributed archives | Keep |
| Draft archive smoke | Downloads/checksums/extracts the actual draft assets before publishing | Keep on all three native runners |
| Production/embed/bundle checks | No test hooks in production, valid static graph, approved bundle budgets | Keep blocking |

GoReleaser builds **six OS/architecture combinations**, but native smoke executes only the archive matching each runner's OS and architecture. Verifying all checksums does not execute all six binaries. Explicitly record the coverage as “six cross-build targets plus three native runner combinations”; add native architecture coverage only if product support warrants its cost.

Do not publish PR snapshot binaries as final releases to save compilation. They use snapshot metadata, were built before the final merge/release decision, and are untrusted PR artifacts. Trusted artifact promotion would need separately designed provenance and source/build-identity guarantees. Frontend-output reuse is a smaller, safer optimization to evaluate first.

The existing release design has useful safeguards: merged-base-code checkout under `pull_request_target`, serialized version selection, draft-first publication, actual-asset smoke checks, and idempotent reruns. Preserve them. Keep PR permissions read-only, capability/security fixtures intact, and plain Go builds independent of Node.

## Proposed responsibility matrix

This is the intended end state, not a description of already-implemented behavior. An always-created classifier and required aggregate sit above these selections.

| Change/event | Native Go matrix and race | Frontend static/unit checks | Functional E2E, including small production startup checks | Snapshot and native archive smoke | Extensive 30-sample performance matrix |
| --- | --- | --- | --- | --- | --- |
| Explicit documentation/instruction-only allowlist | Skip | Skip | Skip | Normally skip; retain any policy-specific packaged-doc validation | Skip |
| Web TS/CSS/assets/dependencies/configuration | Skip ordinary Go matrix unless Go/shared inputs changed | Run | Run | Run | On demand |
| Go source, modules, or shared runtime/fixture dependencies | Run | Conservative selection; full frontend on dependency/config uncertainty | Run conservatively, then refine audited exclusions | Run | On demand |
| Installers, GoReleaser, release scripts, CI infrastructure | Relevant native tests; full selection on uncertainty | Run when frontend/build inputs are involved | Relevant smoke/browser checks; full selection on uncertainty | Run | Only if requested/relevant |
| Unknown paths or failed classification | Run | Run | Run | Run | Separate from correctness |
| Release-label edit | Metadata validation only | — | — | — | — |
| Merge to `main` | No repeated full source matrix | No repeated full frontend suite | Optional short exact-main smoke | Build/version/smoke actual release unless `release:none` | Separate scheduled/on-demand run |

Documentation classification must examine the actual complete diff, not PR titles. PR #101's README-only-looking title covered 25 files, including `main.go` and `web/bundle-budget.json`, so it would not qualify. Root README changes also affect archive contents; skipping the PR snapshot for them is an explicit validation-policy choice, while an actual release must still package the correct document.

## Suggested implementation order

| Phase | Concrete change | Expected effect | Acceptance condition |
| --- | --- | --- | --- |
| 1 | Complete required aggregate; split release-label validation | Fix merge guarantee and stop metadata-triggered rebuilds | Applicable frontend failure blocks merge; label edits do not start/cancel code builds |
| 2 | Frontend concurrency; sensible timeouts; retained failure evidence | Stop superseded work and improve diagnosis | New commit cancels old same-PR checks; independent PRs/releases continue |
| 3 | Conservative classifier; small PR startup checks; separate full measurements | Largest frontend time saving without losing key behavior checks | Docs allowlist skips safely; unknown/dependency changes run checks; startup/security coverage remains |
| 4 | Remove duplicate full main/integration-branch push verification | Eliminate repeated post-merge suite | Full frontend runs once before merge; actual release remains verified; default-branch cache policy is explicit |
| 5 | Reuse built UI modes; trial two frontend jobs or isolated shards | Shorten remaining critical path | Same browser cases pass; no fixture collisions; total runner time and latency both measured |
| 6 | Windows timing/cleanup improvements; selective Vitest environment/cache tuning | Smaller backend/unit gains | Native/race/Node-independent contracts retained; demonstrated improvement across several runs |

A reasonable **experiment target** is to move typical frontend PR feedback from roughly 7–8 minutes toward **3–5 minutes**, then evaluate whether splitting/sharding is still worthwhile. This is not a measured outcome. The strongest measured opportunities are the 105–176 seconds of extra measurements per frontend job, the repeated full `main` run, and unnecessary runs for documentation/labels.

Avoid adding every optimization at once. Record several comparable successful runs before and after each phase, including cold-cache cases. Track PR time to all required checks, cumulative runner seconds, canceled work, setup/build/test time, cache hit/miss, and failure/retry rates. More parallel jobs can reduce waiting while increasing total work.

## Validation for a future implementation

The following cases should be checked in actual GitHub runs and protection settings before declaring the redesign complete:

1. **Frontend-only failure:** typecheck/unit/E2E/bundle failure blocks `main`, even when every backend job succeeds.
2. **Go dependency change:** editing a provider/shared runtime or `go.mod` selects the Go-backed browser coverage even without a `web/` edit.
3. **Docs-only change:** the stable required gate appears, validates classification and metadata, and succeeds without native/build/browser work.
4. **Unknown path/classifier failure:** checks run conservatively or the required gate fails; an accidental skipped job cannot produce a green gate.
5. **Labels:** adding/removing one release label executes the cheap check; conflicting labels fail it; unrelated labels do not restart the heavy workflow.
6. **Successive pushes:** an older same-PR frontend run is canceled; another PR is unaffected; release publication is never canceled by that group.
7. **Merged PR:** there is no second full frontend suite; actual versioned assets are built, tested, and published only after the intended pre-merge guarantees.
8. **No-release merge:** `release:none` skips expensive release setup/build/publication while applicable pre-merge packaging checks still ran.
9. **Production isolation:** snapshot/release/embed checks consume `dist`, never profiling/test output; test hooks remain absent and bundle-budget regressions still fail.
10. **Browser failure:** failure trace/report artifacts exist, fixture processes shut down, and optional long measurements do not continue unless explicitly requested as diagnostics.
11. **Native matrix:** all supported OS jobs remain green; race coverage remains; plain `go build ./...` and `go test ./...` work without frontend installation.
12. **Changed merge policy:** feature-target PRs still receive intended checks; a future merge queue has valid required `merge_group` runs; any allowed direct-push path has an explicit policy.

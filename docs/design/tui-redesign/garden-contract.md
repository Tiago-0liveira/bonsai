# Garden canonical contract

## Identity and index

## Connection and setup (04.2)

The proposed package boundary is `internal/core/garden/connect` (proposed). It resolves remote targets through injected `RemoteLister` and `RepositoryResolver` ports; the current `internal/core/git` has no remote-listing seam, so no shell-backed listing is added here. Garden identity is constructed only from the numeric repository ID. Remotes resolving to the same numeric ID are one candidate and retain their remote names as aliases. Fork/upstream choices with different IDs remain separate candidates. A candidate choice matches by numeric repository ID or exact full name, case-insensitively; partial names never match. A resolver may implement `RepositoryByIDResolver` to add the upstream's display name; otherwise the parent candidate uses a numeric display label.

Remote URLs are sanitized before they reach the resolver: userinfo, query strings, and fragments are removed, including credentials in scp-style remotes. Raw resolver errors and remote URLs never enter returned errors, plans, candidates, or persisted records.

GitHub identity and coding-agent account identity are distinct types; only the GitHub identity label is persisted. Access is None, Read, Write, or Admin with Project scope tracked separately. Read permits observation and never setup. `Connection.Setup()` requires Write/Admin; Project scope is checked for each Project step, so labels-only plans work without it. A Project step without Project scope fails with `ErrScopeMissing`; other steps still complete and the operation remains resumable. Adapter failures are reduced to safe error codes/messages; credentials and raw responses are not retained, and this package never refreshes tokens.

Setup modes are Create, ConnectExisting and Skip. Skip is a durable, reversible association decision. `ConnectExisting` resolves the explicitly selected Project by ID or number through the project read port and verifies both owner and ID; missing/inaccessible Projects and owner mismatch are typed failures. Existing fields are reused by name and only missing desired fields are ensured. Unrelated fields are untouched. A same-name Project is never auto-adopted absent verified ownership; it produces typed `ConflictProject`, blocks Project plan steps, and directs the user to select the Project explicitly with ConnectExisting if it is theirs. Field steps carry the selected Project ID. A Create operation may adopt only when its local operation record shows that this plan attempted creation, the random nonce in that record matches the remote operation marker (the nonce is not derived from repository/GardenID/operation ID), and the Project creator's stable user ID matches the authenticated viewer's stable ID. Unknown creator identity fails closed. Verify against GitHub primary docs when the real adapter lands: whether/how a Project exposes its creator. Plans are pure previews of labels and Project fields. Before each Project create/field write, Apply and Resume re-observe the owner's Projects; before label creation they re-observe labels. A newly appeared compatible label is reused; a conflicting label or unverified same-name Project is surfaced as a conflict and never overwritten. This read-before-write narrows but cannot eliminate the observe/create race: GitHub has no atomic create-if-absent for Projects or labels (to verify). Duplicates from a lost race are surfaced and never silently deleted. Plans assert `ImportCount == 0`; they cannot enroll Issues, rename/delete labels, or edit Issue bodies. Unsupported browser-only finishing is represented by an explicit manual step.

Associations and operations are local-repository scoped, revisioned JSON under Bonsai config, written under the cross-process lock and atomic replacement pattern. Store reads are capped at `connect.MaxStoreBytes` before parsing, require valid UTF-8, reject duplicate keys, unknown fields, trailing data, and unsupported schema versions. Unsupported versions return `ErrUnsupportedSchema`; malformed or oversized stores return `ErrCorruptStore`. Decode errors never rewrite the source file. Idempotency records preserve the original result for Put and Remove replay and reject payload changes. Every remote action has a persisted operation step and sanitized error code. Resume validates the stored plan and hash, requires caller `LocalRepoID` and live access, verifies repository ownership and persisted access, then re-observes remote labels, fields, and Projects. It persists reconciled statuses before any remote write. A foreign or missing operation returns a typed not-found/foreign error without exposing its contents. The nonce used in a Project marker is random and persisted only in the local create step; adoption additionally requires the matching creator and viewer IDs. Concurrent operations for one LocalRepoID fail with `ErrOperationInProgress`; different local clones have separate locks. The config package change adds `GardenAssociationsPath()` to place this store beside project-root configuration; it does not change project-root behavior or data.

A canonical work item is one GitHub Issue, identified by the stable numeric GitHub repository ID and that Issue's stable numeric ID (and node ID when supplied). Title, branch, local path, owner spelling, and repository name are mutable display data, never identity. `GardenID` derives only from the remote repository ID. `LocalRepoID` is the separate path-derived `config.ProjectID`; clones and worktrees share a GardenID while retaining independent local execution identity and locks.

The canonical labels are `bonsai:managed`, exactly one `bonsai:type/feature|bug|chore|research`, and exactly one `bonsai:stage/draft|ready|in-progress|review|blocked|done`. Unknown `bonsai:` labels, missing managed marker, or non-singleton type/stage sets are per-item problems. Issues carrying only a Ready label are not accepted work.

GitHub label names are case-insensitive, so adapters must recognize the `bonsai:` namespace case-insensitively. A case variant of a canonical managed, type, or stage label is still an unknown-namespaced-label problem; writers emit only the exact lowercase canonical spelling.

## Metadata, revisions, and approval

Issue metadata is a JSON envelope with `schema_version: 1`, provenance, owner, acceptance/spec fingerprint, current plan hash, and a bounded `revocations` projection. Each revocation projection entry contains the revoked approval comment ID and revocation comment ID; IDs must be positive and unique and the list is capped at 2,000 entries. Provenance and owner are required. Decoders reject unknown fields for known schemas; unknown future versions return an unsupported-schema problem. Malformed or oversized metadata is reported for that item and never causes the Garden to be erased.

Specs and plans use byte-exact normalization: CRLF and CR become LF, ASCII spaces and tabs at each line end are removed, then leading and trailing LF bytes are removed. No Unicode whitespace is trimmed and no Unicode normalization is performed, so NFC and NFD content hashes differ. Content is SHA-256 addressed.

Revision, approval, and revocation records are append-only GitHub comments. The first line is exactly `<!-- bonsai:garden/v1 {json} -->`; optional human-readable text follows after LF. JSON is bounded by `MaxMetadataBytes`, valid UTF-8, rejects duplicate and unknown fields, and requires `schema_version: 1`; unknown versions are unsupported. Every envelope includes `schema_version`, `kind`, numeric `repo_id`, and numeric `issue_id`. Revision fields are `revision_kind`, `content_hash`, `parents` (hash list), and `source_spec_fingerprint` (required for plans). The normalized comment text after the marker must hash to `content_hash`. Approval fields are `revision_hash`, a required positive `revision_comment_id`, and `source_spec_fingerprint`. Verification accepts an approval only when that exact earlier comment ID is a valid revision envelope for the same issue and its content hash equals `revision_hash`; the ID distinguishes identical-content revisions. Revocation fields are `target_comment_id`. Verification binds every envelope to the requested repo and issue and derives state only from the ordered server comment log, including author IDs and timestamps when supplied. Verification accepts an explicit `Complete` flag; callers must pass false when pagination or retrieval was incomplete. It caps logs at 2,000 comments (`ErrTooManyComments`) and comment bodies at `MaxMetadataBytes + 1 MiB`; overlong bodies are reported per comment.

Approval policy allowlists stable numeric GitHub user IDs; login names are display labels only. Approval and revocation records with a missing author ID are rejected with a per-comment problem. Self-approval is allowed by default; policy may explicitly set `ForbidSelfApproval` to reject it. An approval is valid only when its referenced revision comment occurs earlier in verified order (created time, then server comment ID). Verification sorts a private copy of the log by that order, so input slice order has no effect; a revocation encountered before its target approval is ignored because that target has not yet appeared. Byte-identical duplicate comment IDs collapse to one record; conflicting records with one ID produce a per-comment problem and none is trusted. Heads are evaluated independently for spec and plan revisions: forks are competing heads, while a linear older plan revision does not remove an otherwise accepted specification from Work. On writing a revocation, Bonsai records both approval and revocation comment IDs in metadata. Verify checks every projected revocation; a missing or altered expected revocation reports a problem and keeps its approval invalid. Revocation and supersession invalidate approval; they are explicit records and never mutate prior revision content. Plan approval is valid only while its source-spec fingerprint equals the current spec fingerprint. A changed body/revision head, missing referenced comment, altered comment, unexpected label, or competing head is external-edit/conflict state requiring attention. Lane treats any verification problem in the accepted revision/approval/revocation chain, any incomplete log, and an accepted item without a valid spec head as Attention; malformed unrelated comments without a Garden marker are ignored. Once a spec was accepted, a changed spec head without valid approval is Attention regardless of stage; ideas that have never been accepted remain Draft. A user with Issue write access can edit both comments and the body projection; Garden guarantees integrity against non-privileged commenters and detects inconsistent or accidental edits, not malicious edits by such a writer. Plan 09 must re-verify at launch time and require fresh approval whenever state is inconsistent.

## Lanes and concurrency

Unvalidated ideas remain in Drafts (`draft` stage). A verified specification acceptance moves that same Issue to Work; it does not create another item. Once accepted, a stale plan leaves the Issue in Work and marks its approval stale. A Ready label without verified acceptance is Attention, never Work. Invalid labels or metadata also require Attention.

Lane classification consumes decoded metadata and a `Verification` result. Missing or inconsistent metadata is Attention. Work requires a valid, non-revoked approval for the current spec head and matching accepted-spec hash; competing heads and projection drift are Attention. A stale plan does not remove an otherwise valid accepted specification from Work.

Metadata acceptance requires valid lowercase 64-character SHA-256 `accepted_spec_hash` and `spec_fingerprint`; unaccepted metadata cannot carry an accepted hash. Any present plan hash must have the same format.

A read ETag is not atomic update protection, and read-before-write is not a guarantee. If an adapter cannot establish a documented conditional write, it appends a revision rather than replacing the user's Issue body and exposes competing heads. Before implementing a real adapter, verify conditional writes, pagination, permissions, and payload limits against current primary GitHub documentation; this contract makes no claim about their availability or exact behavior.

## Proposed package paths

These are proposed additions: `internal/core/garden` for domain and narrow ports, `internal/core/garden/fake` for in-memory contract adapters, and a future GitHub-specific adapter under a separately reviewed path. Project fields/views are projections, not a second writable task database. The PR-oriented `internal/git/github.GitHubService` remains unchanged.
